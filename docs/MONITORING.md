# Production monitoring

Yappr has no application backend. `.github/workflows/monitoring.yml` runs static-site smoke checks and read-only Dash Platform probes every 30 minutes, with a manual **Run workflow** option. Schedules start only when the workflow reaches the repository's default branch (`master`); merging it into `staging` alone does not activate the schedule. No client error reporting is added.

The workflow needs only the repository `GITHUB_TOKEN` (`contents: read`, `actions: read`, `deployments: read`, `issues: write`). It never loads a seed, private key, credential file, signer, or state transition. The only writes are monitoring artifacts and GitHub incident issues. There is no chain write mode.

## Checks

- **Sites:** `https://yap.pr/`, `/testing/`, `/staging/`, `/devnet/`, and `https://yappr.pages.dev/` must return HTTP 200. Their embedded Next.js `buildId` must match the expected source commit, and their exported JavaScript bundles (including lazy route chunks) must contain every configured contract id, including the App Connect anchor and members. The page also exposes role-preserving effective contract constants in a `yappr-contract-config` meta tag. The same metadata records the browser SDK network and, on devnet, the devnet name, DAPI pool and quorum URL from the effective SDK constants. The monitor compares these with the intended deployment network and env-derived connection settings, compares the effective social, DM, storefront, blog, profile and Pollr query topologies (using their owning browser configuration), then compares each configured role (including disabled contracts and App Connect version pins); finding an ID in a snapshot is not sufficient. Existing deployments need a rebuild to expose this metadata. Versioned archive mirrors are outside this monitor.
- **Deployment expectations:** the Pages build records its exact master and staging commits, build IDs, environment-derived contract IDs, version pins, and exported chunk paths in the `monitoring-expectations` artifact (90-day retention). The smoke check downloads the artifact of the latest successful `github-pages` **deployment**, even if its workflow subsequently failed or was cancelled; it never learns an expected build from the site it is checking or assumes that the branch tip has deployed. An expired/missing artifact is a monitoring failure: deploy again through the normal reviewed deployment path. The Cloudflare main mirror must match the production commit and contract IDs too. Its independently built asset filenames come from its own page and webpack lazy-chunk table, rather than assuming that Cloudflare and GitHub builds produce identical filenames. A mirror that runs ahead of the gated deployment or fails to follow a rollback alerts until the two sites agree (D29).
- **Contract sets:** production testnet reads `.env.testnet`, `/testing` reads `.env.testing`, and devnet reads `.env.devnet`, all from the exact source checkouts in the deployment artifact. Schema hashes and version expectations are captured at deployment too. A missing artifact alerts but still permits diagnostic chain probes using the monitoring checkout's files; those fallback probes do not establish coverage of the deployed set. Their keys use the `diagnostic/chain/` namespace, so successes cannot close deployed-set incidents. Local runs without a deployment manifest use that namespace too. After the artifact is restored, inspect the anchored checks and manually close any diagnostic incidents; disappearing diagnostic keys do not prove recovery. There are no production/test/devnet ID fallbacks. A missing file or a file with no IDs produces a visible `SKIP` notice, so an unregistered release does not fail. A populated set with a missing contract or missing snapshot fails. Existing incidents for skipped/removed checks stay open until investigated; a skip cannot demonstrate recovery.
- **Contracts:** fetch every configured contract with SDK proof verification, compare its version with its App Connect `id:version` pin (bare App Connect members pin version 1), and compare the SHA-256 of its canonical contract JSON with the committed binary snapshot in `lib/contracts/bundled/`. Non-member contracts take their expected version from that snapshot. The hash covers schema, configuration, tokens and membership as well as identifiers/version, with object keys sorted and array order preserved. No baseline is fetched from the live chain during a check. Refresh and review snapshots whenever registration or an additive update changes the deployment. Include the anchor in the snapshot.
- **App Connect group:** prove group ownership and absence of admins, then page whole-contract, document-type and token memberships and compare the complete set with the pinned whole-contract members. Added members alert even when every pinned contract hash is unchanged. Missing group settings skip visibly; partial pins, missing groups, stale proofs or incomplete pagination fail. Trust rules are shared with the login library.
- **DAPI/quorums:** use the environment's node list or discover enabled testnet nodes from the quorum service. Connect separately to three distinct nodes, prefetch trusted BLS keys, ratchet the SDK with a proved system-contract read, then verify the current epoch, protocol upgrade state and fresh response metadata. The stable `chain/<network>/nodes` check includes each sampled address and its result; any sampled failure alerts, even if the availability check still passes. The status website's summary protocol field is never used. The DCG quorum service is the accepted trust root (D27).
- **Sponsorship:** read balances of every fetched contract owner plus the explicitly pinned group owner/maker. The default minimum is **200,000,000,000 credits = 2 tDASH** (about 12,000¢ at the release record's $60/DASH reference). A missing identity also fails.
- **Moderation:** read elected contracts' moderator fee pots and compare to configurable bounds. Read the charters contract's `electedCharter.byTargetContract` contest, including its winner, and the seated team. Any leader outside the approved allowlist alerts. An unseated team is reported as pending; registration/election readiness remains a release gate in [TESTNET_RELEASE.md](TESTNET_RELEASE.md).
- **Activity:** count retained social `post` and `report` documents created in the last 30 minutes, paging proved queries until complete or over threshold. Report queries include every bounded status value, including resolved reports. Counts above 1,000 posts or 100 reports alert. This is a spam signal, not an accounting ledger: deleted documents disappear, and a live-marker index counts only retained live posts. Missing usable time indexes fail explicitly. It does not record post bodies, reports, private content or identities of posting users in artifacts.

Read checks include a stable key, detail, and elapsed milliseconds. Chain workers have a four-minute deadline each; a timeout/crash creates its own incident without discarding earlier results. Each site has a one-minute deadline; individual HTTP requests and DAPI operations have shorter timeouts. Results are retained for 30 days and summarized on the Actions run.

## Configuration

Set repository Actions variable `MONITOR_THRESHOLDS` to a JSON object containing any overrides:

```json
{"MAKER_MIN_CREDITS":200000000000,"POT_MIN_CREDITS":0,"POT_MAX_CREDITS":1000000000000,"WINDOW_MINUTES":30,"POST_MAX":1000,"REPORT_MAX":100,"NODE_SAMPLE":3,"NODE_MIN":2,"MIN_PROTOCOL":14,"MAX_PROOF_AGE_SECONDS":600}
```

All values must be nonnegative safe integers. The window and maximum proof age must be positive. Sample two to ten nodes, with at least two required healthy nodes. Individual sampled node failures still alert. The default pot minimum is zero because a fresh or recently claimed pot is legitimately empty; the default maximum is 10 tDASH (about 60,000¢ at $60/DASH), prompting a payout review. Tune pot bounds and traffic limits after measuring normal use. These are absolute window limits, not a learned statistical baseline.

Set `MONITOR_CHARTER_LEADERS` to approved leader identity IDs **before filing charters**. Keys are network set (`production`, `testing`, `devnet`), then target contract ID:

```json
{"production":{"TARGET_CONTRACT_ID":["APPROVED_LEADER_ID"]},"devnet":{"TARGET_CONTRACT_ID":["APPROVED_LEADER_ID"]}}
```

Without an entry, only that contract's owner is allowed. This conservative default deliberately alerts on a team led by somebody else; do not simply allowlist a newly observed contender. An unexpected seated leader is also an alert, so a completed hostile contest is not treated as a new baseline. Multiple legitimate candidates may be listed during a planned election. The first 100 contenders are inspected; a saturated result alerts rather than claiming complete coverage.

For local checks (Node 22, `npm ci`):

```sh
node scripts/monitoring/run.mjs --chain-only --network devnet --output /tmp/devnet-monitor.json
node scripts/monitoring/run.mjs --chain-only --network testing --output /tmp/testing-monitor.json
node scripts/monitoring/run.mjs --chain-only --network production --output /tmp/production-monitor.json
# Download the live Pages deployment's monitoring-expectations artifact first.
node scripts/monitoring/run.mjs --sites-only --manifest monitoring-expectations.json
```

Local runs do not open issues. Individual `MONITOR_<THRESHOLD>` environment variables override the JSON configuration for local diagnosis. Only `incidents.mjs` uses GitHub writes; the scheduled workflow calls it after the probe. Never add signing credentials to this workflow.

## Incident response

One open issue per failing check uses the stable title `[monitoring] <check key>` and label `incident`. Subsequent failures update its body with current details and the Actions run link. A successful rerun of that exact check updates and closes its managed issues automatically; skipped checks do not close anything. Only issues carrying the monitor's body marker are managed. If installation, artifact download, or execution fails before a report is written, the workflow opens `[monitoring] monitor/execution`. Subscribe to the `incident` label or repository notifications; an issue is the alert delivery channel.

1. Open the linked Actions run and inspect the complete result artifact. Separate a single node, site, balance, schema, or election failure from a network outage. Rerun manually after checking for a deploy in progress or a brief quorum-key propagation window. A success only establishes health at that moment; GitHub schedules can be delayed and this is not a paging service.
2. For a **site/build mismatch**, compare the recorded source SHAs with the successful Pages deploy, check its environment and asset/cache state, and check the Cloudflare main mirror separately. Do not change expected IDs to match an unexplained bundle. Use the [release rollback procedure](TESTNET_RELEASE.md#5-rollback) when necessary. A deliberate rollback must deploy its own expectation artifact; the scheduled monitor keeps using that deployed artifact.
3. For **missing contracts, hash/version drift, stale proofs, or a protocol mismatch**, stop release activity. Check more nodes and the proved epoch data. A testnet rollback can erase documents even when contracts survive. Compare public deployment IDs and the private registration journal; recovery or re-registration requires the operator's normal review and signing procedure. The monitor never attempts repair.
4. For a **low maker balance**, verify the public identity and recent drain, estimate sponsorship consumption, and ask the funded operator to top up using the normal custody process. Never place keys in Actions. For a **pot alert**, verify the elected team and claim status; team pot claims require CRITICAL authority and can occur at most once per epoch. Zero immediately after a claim is normal.
5. For a **rival contender or unexpected seated team**, verify the approved candidates against the release record, inspect the contest and vote timing, and notify the operator responsible for masternode voting. Never automatically copy the observed leader into the allowlist. Follow the release key-compromise procedure if authority is suspect.
6. For a **traffic/report spike**, inspect public samples and moderation queues with the normal app tools. Coordinate elected moderators, preserve public evidence, and use the abuse/takedown procedure in the release record. Traffic alone is not proof of abuse; do not delete user data or ban users from this workflow.

## Recurring operator work

- Review sponsor drain, pot accrual and outstanding incidents daily. Claim pots only through the normal moderator workflow, respecting the once-per-epoch rule.
- Track App Connect grant expiries and renew before their 90-day limit. Monitoring does not hold credentials or renew grants.
- For every additive contract update: review the new contract, update version pins and snapshots, rebuild web and mobile, and confirm fresh smoke/chain results before announcing it.
- Review leader allowlists during planned charter/team changes, and traffic thresholds after representative use. Keep the private registration journal backed up with mode 0600 and preserve asset-lock outpoints outside git.
- During registration, wire production and staging builds to load `.env.testnet` explicitly: plain `npm run build` does not automatically load that filename. The monitor reads it as the expected production contract set and will flag a build that still uses defaults.
- At go-live, verify that the workflow exists on `master`, run it manually, inspect both active and skipped checks, and confirm that incident creation/update/recovery works. Until `.env.testnet` is populated and production probes pass, monitoring is installed but production-chain coverage is pending.
