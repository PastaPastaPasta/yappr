# Testnet configuration and cut-over

The preparation PR adds an opt-in release build mechanism. It does **not**
activate the release, register contracts, change today's `build` command, change
mobile's testnet variant, or change any hosting settings. `.env.testnet.template`
is documentation, never an automatically loaded Next env file. Production,
`/staging`, `/testing` and `/devnet` keep their current configurations.

## Release configuration

After registration, copy `.env.testnet.template` to the checked-in
`.env.testnet`. All values are public. Never copy credentials, private journals,
seed phrases or signing keys into it. Fill the public IDs from the registration
journal and confirm them with proved readback, including actual contract
versions. The release set uses social v17, storefront v10, blog v9, pollr v8,
DM v5 and profile v2. The passkey-vault contract must be registered and its client
landed before cut-over. The unified profile and system contracts are not group
members; grant them separately.

`npm run build:release` loads `.env.testnet` explicitly, replaces ambient
`NEXT_PUBLIC_*` values and `STORAGE_EPOCH` with this file's values (including
blanks), forces `NEXT_PUBLIC_RELEASE=1`, validates, then runs `next build`. It requires Node
20.12 or later (`util.parseEnv`); CI uses Node 22 and the IPFS Node 20 image
must meet that minimum.
It never delegates to `npm run build`, so switching that command cannot recurse.
A missing file or missing/malformed required value fails with a list of errors.
`next.config.js` also validates release mode during the production build phase,
after Next has loaded its env files. Plain development, Vitest and non-release
builds do not validate application constants at module scope.

The gate requires 32-byte base58 contract/identity/token IDs, the release
topologies and App Connect protocol, and exactly the release group's members,
including the anchor and passkey vault. Every member must spell out `id:version`
(even `:1`); duplicate members, extra members, unsafe versions and duplicate
contract roles fail. Retired DM v3/v4, key exchange, password vault, old vault
and key backup IDs, plus all devnet endpoint overrides, must be explicitly
blank. Release mode also requires a non-empty storage epoch and the D23 product
flags (Store/Blog `beta`, credit tips `off`). `NEXT_PUBLIC_YAPP_TOKEN_ID` is a
release audit pin: runtime YAPP remains derived from the social ID at token
position 0. Compare the pin with the SDK's `tokens.calculateId(socialId, 0)`
readback during registration verification. The build gate validates syntax and
configuration consistency, not on-chain ownership, schemas or token derivation;
`verify-appconnect` and registration readback remain mandatory.

There is deliberately no `.env.production`: Next would load it into `/testing`
and `/devnet` for any key those files omit. Keep their configurations separate.
Do not configure `.env.local` or `.env.production*` on release builders. The
template covers public application configuration; `BASE_PATH`, Git metadata and
`NEXT_PUBLIC_STORAGE_SCOPE` are generated by `next.config.js`.

## Storage clean start (D21)

`next.config.js` computes `NEXT_PUBLIC_STORAGE_SCOPE` from `STORAGE_EPOCH` and

`testing`, and devnet `devnet`, exactly as today. At cut-over,

## Cloudflare response headers (owner action)

`yap.pr` uses GitHub Pages behind Cloudflare. GitHub Pages cannot set these
response headers, and a CSP meta tag cannot enforce `frame-ancestors`. Configure
Cloudflare **Rules → Transform Rules → Modify Response Header** on the proxied
`yap.pr` hostname (and apply equivalent rules to each active mirror):

1. For **all paths**, set static response headers:
   - `Strict-Transport-Security: max-age=31536000`
   - `Referrer-Policy: strict-origin-when-cross-origin`
2. For **all paths except embed routes**, set static response headers:
   - `Content-Security-Policy: frame-ancestors 'none'`
   - `X-Frame-Options: DENY`

The second rule's Cloudflare expression is:

```text
(http.host eq "yap.pr" and not (
  http.request.uri.path eq "/embed" or starts_with(http.request.uri.path, "/embed/") or
  http.request.uri.path eq "/staging/embed" or starts_with(http.request.uri.path, "/staging/embed/") or
  http.request.uri.path eq "/testing/embed" or starts_with(http.request.uri.path, "/testing/embed/") or
  http.request.uri.path eq "/devnet/embed" or starts_with(http.request.uri.path, "/devnet/embed/")
))
```

Keep both anti-framing headers absent on these embed routes. If another rule or
origin already sets them, remove them for the embed paths in a later rule.
`/embed.js` (including deployment-prefixed copies) remains usable as a script;
these document framing headers do not restrict script inclusion. Preserve the
existing CSP directives if adding `frame-ancestors` to an existing header.
Do not enable HSTS `includeSubDomains` or `preload` without separately confirming
HTTPS coverage for every affected hostname.

Purge cached HTML after applying the rules. Verify response headers on `/`,
`/login/`, `/staging/`, `/testing/`, `/devnet/` and an unknown/404 path, then verify
that a foreign-origin iframe is rejected by the browser. Check that `/embed/`
and each prefixed embed route still load from a foreign parent, including via
`embed.js`. Repeat for mirrors. The root layout also keeps providers, sign-in
and key inputs unmounted until it verifies that every ancestor is same-origin;
embed routes explicitly skip this fallback guard. The Cloudflare headers remain
the primary defence and must be configured before release.
