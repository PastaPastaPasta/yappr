# App Connect profile: request v2

This is the profile Yappr proposes to wallets for App Connect logins on Platform protocol version 14 and later. Platform standardises only where the response lives: the App Connect system contract `H8F9mP1BM55TE1ShsxPZHzhyinaMdY9bMmP85mkDhcJJ`, document type `loginKeyResponse` (platform `docs/protocol/app-connect.md`). The request format, the keys a wallet grants and how the response binds to the request are left to wallets and apps. This profile fills that gap, and it is meant to work for any app, not only Yappr.

The shared implementation is `vendor/platform-auth/src/app-connect/` (request codec, crypto, verifier, poller, key-ring selector, error mapping). The [test vectors](#test-vectors) at the end are generated by that code and checked by its tests; wallet implementations should reproduce them byte for byte.

**Status:** proposal. Nothing in Yappr uses it yet; the web and mobile login switch to it in later PRs, after the anchor contract exists. The legacy key exchange keeps running on PV13 networks.

## Why a v2 request

The v1 request (`dash-key:` body version `0x01`, `v=1`) names one contract, and the iOS draft (dashwallet-ios#1202) answers it with one `singleContract`-bound key. An app that spans several contracts, such as Yappr with a social contract, DMs, blocks, a blog, polls and a store, needs:

- a key bound to a **contract group** (one key for all the app's contracts);
- a key bound to one **system document type** (the DashPay `profile`);
- a contract-bound **encryption key** that peers can look up;
- **limits** (a budget and an expiry) on each key;
- something that lets the app tell **which identity** should answer, and lets the wallet **supersede** a previous login from the same device.

v2 carries all of this. It uses a new version byte and `v=2`, so a wallet that only knows v1 refuses it instead of granting a key the app cannot use.

## Flow

1. The app makes a fresh ephemeral secp256k1 key pair and shows the request as a QR code and a `dash-key:` link.
2. The wallet decodes it, checks it, and shows an approval sheet.
3. On approval, the wallet derives the keys, registers them in one MASTER-signed IdentityUpdate (which also disables this device's previous grant), waits for it to be confirmed, and publishes a `loginKeyResponse` under the approving identity.
4. The app polls for responses to `hash160(appEphPub)`, decrypts each candidate, and verifies every granted key on chain before it treats anyone as logged in.

## Request

### URI

```
dash-key:<base58(body)>?n=<m|t|d>&v=2[&cb=<percent-encoded https URL>]
```

- `n`: the network, `m` mainnet, `t` testnet, `d` devnet.
- `v`: exactly `2`.
- `cb`: optional return URL (see [Callback](#callback)).
- `n`, `v` and `cb` may each appear once; repeating one makes the URI invalid. Other query parameters are ignored.

### Body

```
body = 0x02 ‖ appEphPub (33) ‖ appId (32) ‖ labelLen (1) ‖ label (labelLen) ‖ TLV*
TLV  = type (1) ‖ length (1) ‖ value (length)
```

| Field | Rule |
| --- | --- |
| version | `0x02` |
| `appEphPub` | compressed secp256k1 point, fresh for every request |
| `appId` | the app's id: the contract id the wallet brands the request with and checks ownership against |
| label | UTF-8, at most 64 bytes, without C0/C1 control characters or bidirectional formatting characters; shown on the approval sheet only as a hint (the brand comes from `appId`) |

TLV rules:

- **Even types are mandatory to understand.** A wallet that meets an unknown even type refuses the request as `unsupported`.
- **Odd types are optional.** A wallet skips unknown odd types.
- TLVs appear in **ascending type order**. Among known types only `AUTH_BINDING` and `ENC_BINDING` repeat; an unknown odd type may repeat too (a future optional type might). Repeats are adjacent. Anything out of order, a repeated known singleton, a known type with the wrong length or value, or a TLV running past the end makes the request `invalid`. So every request has exactly one encoding.
- Integers are big-endian.

| Type | Name | Count | Value |
| --- | --- | --- | --- |
| `0x01` | `IDENTITY_HINT` | 0–1 | identity id (32) the app expects to answer |
| `0x02` | `AUTH_BINDING` | 1–4 | see below |
| `0x03` | `CONNECTION_ID` | 0–1 | 16 random bytes, one per (app install, network) |
| `0x04` | `ENC_BINDING` | 0–2 | contractId (32) ‖ purpose (1): `1` ENCRYPTION, `2` DECRYPTION |
| `0x05` | `MODE` | 0–1 | `1` renew. Absent means login; any other value is invalid. |
| `0x06` | `CREATED_AT` | 1 | u64, milliseconds since the epoch |

`CREATED_AT` and at least one `AUTH_BINDING` are required.

### AUTH_BINDING

```
kind (1) ‖ securityLevel (1) ‖ id (32) ‖ totalBudget (u64) ‖ expiresAt (u64) [‖ nameLen (1) ‖ name]
```

| Field | Rule |
| --- | --- |
| kind | `0` singleContract, `1` documentType, `2` contractGroup (Platform's `ContractBounds` bincode tags). An unknown kind is `unsupported`. |
| securityLevel | `1` CRITICAL only on a contractGroup binding; `2` HIGH on every kind. Anything else is invalid. |
| id | the contract id, or the group id for contractGroup |
| totalBudget | proposed lifetime budget in credits; `0` means none. **A contractGroup binding must carry one.** |
| expiresAt | proposed expiry as a block time in milliseconds; `0` means none |
| name | documentType only: the document type name, 1–64 bytes of `[A-Za-z0-9_-]`. Absent on the other kinds. |

The **first** `AUTH_BINDING` is the primary binding. A wallet may decline any other binding (for example the user unticks "edit your DashPay profile"), but declining the primary one declines the whole request. Bindings may not repeat (same kind, id and name).

Budget and expiry are **proposals**: the app proposes, the wallet clamps and lets the user pick from presets, and the chain records what was granted. A wallet may change the values but must not drop a limit the request asked for, and must never grant a contractGroup key without a budget.

### Callback

`cb` is an absolute `https` URL without credentials, at most 512 characters. The wallet:

- opens it only if it is `https` and its host is one the wallet associates with `appId` (its brand map); otherwise it shows the host and asks, or does not open it;
- shows the host on the approval sheet, and warns when a branded `appId` arrives without a `cb` on one of its hosts (the host is the user's main phishing signal);
- appends `ac=<status>` to it (keeping any existing query) when it is done:

| `ac` | Meaning |
| --- | --- |
| `ok` | keys registered and the response published |
| `declined` | the user declined |
| `stale` | the request was too old or too far in the future |
| `unsupported` | an unknown version, even TLV or binding kind |
| `invalid` | malformed, or it breaks a wallet rule (owner consistency, levels, budget) |
| `failed` | approved, but registering or publishing failed |

The callback is only a nudge: the app polls immediately when it arrives and never treats it as proof of anything.

### Size

Yappr's request (two auth bindings, one encryption binding, a connection id) is a 247-byte body. With a callback URL the URI is 435 characters, which fits a QR code of version 14 at error correction L; without one it fits version 12.

## Response

The wallet publishes a `loginKeyResponse` under the approving identity:

| Property | Value |
| --- | --- |
| `appEphemeralPubKeyHash` | `hash160(appEphPub)` |
| `walletEphemeralPubKey` | the wallet's fresh compressed ephemeral public key |
| `encryptedPayload` | `nonce (12) ‖ ciphertext ‖ tag (16)` |

### Crypto

```
shared = ECDH(walletEphPriv, appEphPub).x                         (32 bytes)
key    = HKDF-SHA256(ikm = shared, salt = "dash:key-exchange:v1", info = "app-connect:v2", 32 bytes)
aad    = "dash:app-connect:v2" ‖ hash160(appEphPub) ‖ $ownerId      (19 + 20 + 32 bytes)
body   = AES-256-GCM(key, nonce, aad, slot₀ ‖ slot₁ ‖ … ‖ slotₙ₋₁)
```

- The salt is the legacy key exchange's; the `info` string is new, so a v2 key never equals a v1 key.
- `$ownerId` is the raw 32-byte id of the identity that publishes the response. A response copied under another identity does not decrypt.
- The nonce is 12 random bytes, fresh per response.

### Payload

Each slot is a 32-byte secp256k1 private key. Slots are ordered: granted auth bindings in request order, then granted encryption bindings in request order. A declined binding has no slot. The payload is `28 + 32n` bytes with `1 ≤ n ≤ 17` (the schema's 60–572 bytes); for v2, `n` is at most the number of bindings.

The app does **not** rely on slot order: it classifies each key by finding it on chain.

## Wallet rules

1. **Decode strictly.** Refuse with `unsupported` or `invalid` as above.
2. **Freshness.** Refuse a request whose `CREATED_AT` is more than 10 minutes before the wallet's clock, or more than 2 minutes after it (`stale`).
3. **Owner consistency.**
   - A contractGroup or singleContract binding must be owned by the owner of `appId` (the group's owner, or the contract's owner).
   - A documentType binding on a contract owned by someone else is allowed only for system document types the wallet allowlists. This profile allowlists exactly one: DashPay `profile`. Never DashPay `contactRequest`, and never DPNS.
   - An `ENC_BINDING` contract must be `appId`, and that contract must opt in to identity encryption (or decryption) bounded keys for that purpose.
4. **Levels.** A contractGroup key may be CRITICAL or HIGH, never above what the binding asks. Every other auth key is HIGH. Encryption and decryption keys are MEDIUM. A wallet never grants a MASTER key, an unbound authentication key or a TRANSFER key through App Connect.
5. **Limits.** Every auth key is a V1 key. Clamp the proposals and offer presets:

   | | Presets | Cap |
   | --- | --- | --- |
   | Budget | 0.1 / 0.5 / 2 DASH | 5 DASH |
   | Lifetime | 30 / 90 / 365 days | 365 days |

   A contractGroup key always has a budget.
6. **Auth key derivation.** One fresh key per granted auth binding, at the DIP-13 App Connect leaf with DIP-14 256-bit hardened indices:

   ```
   …/6'/0'/identityId'/hash256(appEphPub)'/bindingIndex'
   ```

   `bindingIndex` is the binding's position in the request (0–3), so the leaf does not depend on what the user declined. Keys may be ECDSA_SECP256K1 or ECDSA_HASH160. (This extends the dips#191 leaf with the binding index.)
7. **Encryption key.** One key per (identity, `appId`), shared by every device, derived at DIP-13 sub-feature `7'` from (identity, `appId`, rotation index). It is ECDSA_SECP256K1 (peers need the point), MEDIUM, bound `singleContract(appId)`.
   - If the identity's current key for `appId` (what `identities.contractKeys` returns) is one this wallet can derive, **re-send it** and register nothing.
   - If the identity has none, register rotation 0 and send it.
   - If it has one this wallet cannot derive (another wallet made it), **omit the slot**.
   - **Never rotate silently.** A new rotation orphans everything peers encrypted to the old key; it is an explicit user action, not part of a login.
8. **One identity update.** A single MASTER-signed IdentityUpdate adds the new keys (and the encryption key if it was missing) and disables the auth keys of the previous grant for the same (identity, `appId`, `CONNECTION_ID`). Without a `CONNECTION_ID` nothing is disabled. Platform adds at most 6 keys per update, which this profile never exceeds (4 auth + 2 encryption).
9. **Publish.** Wait until the update is confirmed. Then delete the previous response the wallet published for this identity and app, using an index-only delete carrying all three original values, and create the new response. Both may go in one batch, signed by the identity's own unbound HIGH key.
10. **Callback.** Open `cb` as described above.

### Approval sheet

Say what the app can do, what it can spend, and for how long, in plain words, and say what it cannot do. Yappr's sheet should read close to:

> **Yappr** wants to sign in as **@alice**.
>
> Yappr can post, like, follow, message and edit your DashPay profile, spending up to **0.5 DASH** until **9 January 2027**. It cannot send your credits, register names or change your keys.
>
> Requested 12 seconds ago · returns to yap.pr
>
> Only approve if you just started signing in on yap.pr.

- Brand from `appId` (the brand map), not from the label. An unknown `appId` shows its id and the label in quotes, with a warning.
- One line per granted binding; optional bindings are toggles.
- Show the budget in DASH, not credits, and the expiry as a date.
- Show the request age and the callback host.
- For a CRITICAL group key, the line about tokens: "It can also claim and spend this app's tokens on your behalf."

## App rules

These are what `vendor/platform-auth/src/app-connect/` implements.

**Polling.** Query `loginKeyResponse` with `appEphemeralPubKeyHash == hash160(appEphPub)`, ordered by `$ownerId`, 10 per page, paging after the last owner; with a hint, add `$ownerId == hint`. Poll every 2 s for the first minute, then every 4 s, and immediately on focus or callback. Give up after 10 minutes, or after 20 candidates ("start again").

**Verification.** A candidate is accepted only if all of these hold, with proved reads:

1. With an `IDENTITY_HINT`, the candidate's `$ownerId` equals it.
2. The payload framing is `28 + 32n`, with `n` no larger than the number of bindings, and it decrypts with the AAD.
3. Every slot is a key on `$ownerId` (by point for ECDSA_SECP256K1, by `hash160` for ECDSA_HASH160) that is not disabled.
4. Every auth key has bounds equal to one requested binding, an allowed level for it (rule 4), and the limits the binding asked for, including the group key's budget.
5. Every encryption key is MEDIUM, ECDSA_SECP256K1, bound `singleContract` to an `ENC_BINDING` contract with the same purpose, and is the key `identities.contractKeys` currently returns.
6. No key is MASTER, unbound, of another purpose, bound to anything not requested, or granted twice; no binding gets two keys.
7. The primary binding is granted.
8. No key expires within an hour of the latest block time, and every budgeted key has a remaining budget above zero.

Anything else rejects the whole candidate. A key that is not visible yet is retried for a few seconds (the app's node may lag the wallet's).

**Identity confirmation.** Anyone can answer a request, including with their own identity. With a hint, only that identity is accepted. Without one, the app always asks "Continue as @alice?" with the avatar and name, and offers a chooser when several candidates verify.

**Group trust.** Before offering App Connect, the app proves that the group's owner and admins are the ones it pinned and that its members are exactly the pinned set. A group-bound key may sign for every member the group ever gains, so an unexpected member or owner blocks new logins.

**Signing.** The session is a key ring. Before building a write, the app picks the narrowest usable key that covers every batch member (a documentType key, then a contract key, then the group key, using the pinned members), including every document type a create consumes. It requires CRITICAL for any batch with a token operation and the strictest `securityLevelRequirement` of the members' types, never uses a bound key outside a batch, skips keys about to expire or short of budget, and splits a batch no single key covers (a DashPay profile plus a Yappr profile). As long as the caller describes the batch accurately, the paid out-of-bounds refusal (20014) cannot happen.

## Errors

| Code | Platform error | App action |
| --- | --- | --- |
| 20013 | `ContractBoundedKeyNonBatchError` | A routing bug: send the write to the wallet and log it. Unpaid. |
| 20014 | `ContractBoundedKeyOutOfBoundsError` | Should be impossible. Paid. Drop cached budgets and bounds, show a generic error, log loudly. |
| 20015 | `PublicKeyBudgetExhaustedError` | The allowance is spent. Reads continue; ask to renew. Unpaid. |
| 20016 | `PublicKeyExpiredError` | The key expired. Reads continue; ask to renew. Unpaid. |
| 40218 | `IdentityPublicKeyBudgetExceededError` | This write needs more than is left. Say how much, then ask to renew. Unpaid. |
| 20006, 40208 | key disabled | Revoked in the wallet: sign out and wipe the session. |
| 20003 | `MissingPublicKeyError` | The key is gone: sign out and wipe the session. |
| 20004, 20007 | security level not met | Send the write to the wallet. 20004 is paid when a batch member's type requires a higher level. |

**Renewal** (phase 2, `MODE = 1`): the wallet raises the limits of the existing keys with `IdentityKeyLimitsUpdate` and republishes. Until wallets support it, renewal is a new login carrying the same `CONNECTION_ID` and the identity as `IDENTITY_HINT`, which supersedes the old keys.

## Yappr's request

| | Value |
| --- | --- |
| `appId` | the `yappr-app` anchor contract (registered with the beta.4 cut-over; it creates the group, opts in to `requiresIdentityEncryptionBoundedKey: 2`, and has one owner-only `appInfo` type) |
| label | `Yappr` |
| Binding 0 (primary) | contractGroup, the anchor's group, **CRITICAL**, 50,000,000,000 credits (0.5 DASH ≈ $30), 90 days |
| Binding 1 | documentType, DashPay `Bwr4WHCPz5rFVAD87RqTs3izo4zpzwsEdKPWUT1NS1C7` `profile`, HIGH, 1,000,000,000 credits (0.01 DASH ≈ 60¢), 90 days |
| `ENC_BINDING` | the anchor, ENCRYPTION |
| `CONNECTION_ID` | 16 random bytes per browser or device and network, kept across logouts |
| `cb` | `https://yap.pr/connect?r=<hex hash160(appEphPub)>` |

The group has no admins. Its members are the anchor, social v15, blocks, DM v5, blog, pollr, storefront and the auth vault. The legacy key exchange, password vault, key backup and DM v4 contracts stay out of it. 0.5 DASH is roughly 300 posts or 3,000 likes at current fees.

**Why CRITICAL.** Platform requires CRITICAL for any batch that contains a token transition, and Yappr's 100-YAPP starter claim is one. Bound to the group, a CRITICAL key adds only token operations on the group's tokens: YAPP cannot be transferred and the user holds no token authority, so in practice that is claiming and spending the user's own YAPP. The app still signs every other write with the narrowest key, and accepts a HIGH group key (the claim is then unavailable in the app).

**Still outside App Connect** (wallet `dash-st:` links or native wallet flows): credit tips (TRANSFER), DPNS registration, revoking keys and raising limits, and contract moderation.

## Plan B: v1 plus a brand map

If wallet teams prefer not to ship v2, an app can send a v1 request whose contract id is its anchor, and the wallet's brand-map entry for that anchor defines the binding set and limits (for Yappr: the group key, the DashPay profile key and the anchor encryption key). The app-side verifier is the same. Plan B loses the request-carried limits, the identity hint, connection-id supersession and the AAD, so it is a fallback, not the proposal.

## Test vectors

All inputs are fixed so the outputs are reproducible. Each 32-byte seed is `sha256("dash app-connect v2 vector/" + label)`: `app ephemeral`, `wallet ephemeral`, `app id`, `group id`, `owner`, `slot group key`, `slot dashpay profile key`, `slot encryption key`; the connection id is the first 16 bytes of `sha256(… "connection id")` and the nonce the first 12 bytes of `sha256(… "nonce")`. The request is Yappr's (with placeholder anchor and group ids), created at 2026-10-11T00:00:00Z with both keys expiring 90 days later, on devnet with a callback. The renew request is the same with only the group binding, `IDENTITY_HINT` = the owner and `MODE` = renew, on testnet without a callback.

- `request.bytes` is the body; `request.uri` the URI.
- `response.sessionKey` is the HKDF output; `response.aad` the AAD; `response.plaintext` the three slots concatenated (group, profile, encryption).
- `response.encryptedPayload` is the nonce, ciphertext and tag; `response.slotPublicKeys` and `response.slotPublicKeyHashes` are what the identity update registers (as ECDSA_SECP256K1 or ECDSA_HASH160 data).

`vendor/platform-auth/src/app-connect/vectors.json` holds the same values, and `vectors.test.ts` checks that the code reproduces them, that this block matches, and that an independent AES-256-GCM decrypts the payload.
