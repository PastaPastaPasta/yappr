# App Connect profile: request v2

This is the protocol reference for App Connect: how a Dash wallet signs a user in to an app on Platform protocol version 14 and later, and how (as planned) it signs one state transition for the app. It stays the reference until a DIP replaces it. Platform standardises only where the response lives: the App Connect system contract `H8F9mP1BM55TE1ShsxPZHzhyinaMdY9bMmP85mkDhcJJ`, document type `loginKeyResponse` (platform `docs/protocol/app-connect.md`). The request format, the keys a wallet grants and how the response binds to the request are left to wallets and apps. This profile fills that gap, and it is meant to work for any app, not only Yappr. The sections about Yappr's own request and sign-in options come after the protocol.

The shared implementation is `vendor/platform-auth/src/app-connect/` (request codec, crypto, verifier, poller, key-ring selector, error mapping). The [test vectors](#test-vectors) at the end are generated by that code and checked by its tests; wallet implementations should reproduce them byte for byte.

See [Planned carriers](#planned-carriers) and [App identity](#app-identity).
> - **Shipping today.** The same request v2 body on the transitional carrier `dash-key:<base58>?n=&v=2[&cb=]`. The response, keys and verification in this document are what runs. Wallet side: dashwallet-ios TestFlight 9.1.4 (12), from the unmerged PRs #1202/#1204/#1210, and dash-wallet PR #1604 (open; grants `contractGroup` bindings after verifying the group's members and admins). App side: Yappr web and mobile builds with `NEXT_PUBLIC_LOGIN_PROTOCOL=app-connect` (the testnet, devnet and beta env files) emit and verify it. The production root and `/testing` still use the legacy key exchange until the cut-over.
> - **Not implemented yet.** `dashpay://connect` and `dashpay://sign` exist in no wallet and Yappr does not emit them. Everything under "Planned" below is a design, and there are no test vectors for it yet.
> - **Legacy.** `dash-key:` v1 and `dash-st:` are the first key exchange. They go before mainnet, and so does the `dash-key:` v2 carrier. Yappr still uses `dash-st:` for tips, YAPP purchases and messaging-key setup until those move to `dashpay://sign`.
> - **DIP work.** dashpay/dips#191 (the DIP-13 derivation paths) and dashpay/dips#181 (to be rewritten as the App Connect DIP). Once that DIP exists, this profile shrinks to what Yappr requests and links to the DIP.

## Why a v2 request

The v1 request (`dash-key:` body version `0x01`, `v=1`) names one contract, and the iOS draft (dashwallet-ios#1202) answers it with one `singleContract`-bound key. An app that spans several contracts, such as Yappr with a social contract, DMs, blocks, a blog, polls and a store, needs:

- a key bound to a **contract group** (one key for all the app's contracts);
- a key bound to one **system document type** (the DashPay `profile`);
- a contract-bound **encryption key** that peers can look up;
- **limits** (a budget and an expiry) on each key;
- something that lets the app tell **which identity** should answer, and lets the wallet **supersede** a previous login from the same device.

v2 carries all of this. It uses a new version byte and `v=2`, so a wallet that only knows v1 refuses it instead of granting a key the app cannot use.

## Flow

1. The app makes a fresh ephemeral secp256k1 key pair and shows the request as a QR code and a link (today a `dash-key:` link, planned `dashpay://connect`).
2. The wallet decodes it, checks it, and shows an approval sheet.
3. On approval, the wallet derives the keys, registers them in one MASTER-signed IdentityUpdate (which also disables this device's previous grant), waits for it to be confirmed, and publishes a `loginKeyResponse` under the approving identity.
4. The app polls for responses to `hash160(appEphPub)`, decrypts each candidate, and verifies every granted key on chain before it treats anyone as logged in.

## Request

### Carrier today: `dash-key:` v2

```
dash-key:<base58(body)>?n=<m|t|d>&v=2[&cb=<percent-encoded https URL>]
```

- `n`: the network, `m` mainnet, `t` testnet, `d` devnet.
- `v`: exactly `2`.
- `cb`: optional return URL (see [Callback](#callback)).
- `n`, `v` and `cb` may each appear once; repeating one makes the URI invalid. Other query parameters are ignored.

This carrier is transitional: wallets that speak `dashpay://connect` keep accepting it until the apps have switched, and it is removed before mainnet. A session does not depend on the carrier it was made through. The app holds the keys, the chain holds their bounds and limits, and the wallet's grant record is keyed by (identity, `appId`, `CONNECTION_ID`), so a session made through `dash-key:` keeps working until it expires, runs out of budget or is disconnected.

### Body

```
body = 0x02 ‖ appEphPub (33) ‖ appId (32) ‖ labelLen (1) ‖ label (labelLen) ‖ TLV*
TLV  = type (1) ‖ length (1) ‖ value (length)
```

| Field | Rule |
| --- | --- |
| version | `0x02` |
| `appEphPub` | compressed secp256k1 point, fresh for every request |
| `appId` | the app's id: the contract id that names the app and that ownership is checked against (see [App identity](#app-identity)) |
| label | UTF-8, at most 64 bytes, without C0/C1 control characters or bidirectional formatting characters. The app writes it and nothing verifies it: the wallet shows it as the app's own claim, never as a verified name |

TLV rules:

- **Even types are mandatory to understand.** A wallet that meets an unknown even type refuses the request as `unsupported`.
- **Odd types are optional.** A wallet skips unknown odd types.
- TLVs appear in **ascending type order**. Among known types only `AUTH_BINDING` and `ENC_BINDING` repeat; an unknown odd type may repeat too (a future optional type might). Repeats are adjacent. Anything out of order, a repeated known singleton, a known type with the wrong length or value, or a TLV running past the end makes the request `invalid`. So every request has exactly one encoding.
- Integers are big-endian.

| Type | Name | Count | Value |
| --- | --- | --- | --- |
| `0x01` | `IDENTITY_HINT` | 0–1 | identity id (32) the app expects to answer |
| `0x02` | `AUTH_BINDING` | 1–4 | see below |
| `0x03` | `CONNECTION_ID` | 0–1 | 16 random bytes, one per (app install, network) |
| `0x04` | `ENC_BINDING` | 0–2 | contractId (32) ‖ purpose (1): `1` ENCRYPTION, `2` DECRYPTION |
| `0x05` | `MODE` | 0–1 | `1` renew. Absent means login; any other value is invalid. |
| `0x06` | `CREATED_AT` | 1 | u64, milliseconds since the epoch |

`CREATED_AT` and at least one `AUTH_BINDING` are required.

### AUTH_BINDING

```
kind (1) ‖ securityLevel (1) ‖ id (32) ‖ totalBudget (u64) ‖ expiresAt (u64) [‖ nameLen (1) ‖ name]
```

| Field | Rule |
| --- | --- |
| kind | `0` singleContract, `1` documentType, `2` contractGroup (Platform's `ContractBounds` bincode tags). An unknown kind is `unsupported`. |
| securityLevel | `1` CRITICAL only on a contractGroup binding; `2` HIGH on every kind. Anything else is invalid. |
| id | the contract id, or the group id for contractGroup |
| totalBudget | proposed lifetime budget in credits; `0` means none. **A contractGroup binding must carry one.** |
| expiresAt | proposed expiry as a block time in milliseconds; `0` means none |
| name | documentType only: the document type name, 1–64 bytes of `[A-Za-z0-9_-]`. Absent on the other kinds. |

The **first** `AUTH_BINDING` is the primary binding. A wallet may decline any other binding (for example the user unticks "edit your DashPay profile"), but declining the primary one declines the whole request. Bindings may not repeat (same kind, id and name).

Budget and expiry are **proposals**: the app proposes, the wallet clamps and lets the user pick from presets, and the chain records what was granted. A wallet may change the values but must not drop a limit the request asked for, and must never grant a contractGroup key without a budget.

### Size

Yappr's request (two auth bindings, one encryption binding, a connection id) is a 247-byte body. As a `dash-key:` URI with the test-vector callback URL (Yappr's real callback differs slightly) it is 435 characters, which fits a QR code of version 14 at error correction L; without one it fits version 12. As `dashpay://connect` the same request is 439 characters with the same test-vector callback and 358 without, which fit the same versions.

## Planned carriers

> **Planned. Not implemented in any wallet or app.** The body is the request v2 body above, unchanged. Only the carrier changes. Test vectors for these URIs will be added when they are implemented.

### `dashpay://connect`

```
dashpay://connect?v=2&n=<m|t|d>&r=<canonical base64url(body)>[&cb=<percent-encoded https URL>]
```

| Part | Rule | Refusal (`ac`) |
| --- | --- | --- |
| Whole URI | at most 4,096 bytes of UTF-8, checked on the raw string before any decoding | `invalid` |
| `r` | required; canonical base64url; at most 1,366 characters, decoding to at most 1,024 bytes | `invalid` |
| body | decoded under every rule of this profile; an unknown version byte, even TLV or binding kind is `unsupported` | `unsupported` or `invalid` |
| freshness | `CREATED_AT` at most 10 minutes behind the wallet's clock and at most 2 minutes ahead. There is no `exp`: a second clock field could disagree with `CREATED_AT` | `stale` |

### `dashpay://sign`

```
dashpay://sign?v=2&n=<m|t|d>&exp=<unix seconds>&st=<canonical base64url(unsigned state transition)>[&app=<base58 app id>][&cb=<percent-encoded https URL>]
```

| Part | Rule | Refusal (`ac`) |
| --- | --- | --- |
| Whole URI | at most 8 KiB when read by the wallet's in-app scanner; at most 28 KiB when the OS delivers it (a tapped link or a system-camera scan) | `invalid` |
| `exp` | ASCII digits, at most 11, Unix seconds. Refused when `exp` is not in the future or is more than an hour plus 2 minutes ahead. Checked again right before signing | `stale` |
| `st` | required; canonical base64url; decodes to 1 to 20,480 bytes (Platform's maximum state transition size) | `invalid` |
| `app` | optional app id, used only to say "Requested by app …" and to explain why the app's own session key could not do this. Never used to skip a check | `invalid` if malformed |

### Rules shared by both verbs

- **Scheme and host.** The scheme is `dashpay`; the host is the verb. Emitters write both in lowercase (Android intent filters match case-sensitively); wallets compare them case-insensitively. A host the wallet does not know shows "this link needs a newer version", not a generic error. The path is empty (a lone `/` is ignored), with no userinfo, port or fragment.
- **Query.** Split on `&`, form-decode names and values. A repeated known parameter refuses the request; unknown parameters are ignored. Emitters write parameters in the order shown above so that vectors are byte-exact; wallets accept any order.
- **`v`.** Exactly `2` for each verb; anything else is `unsupported`.
- **`n`.** Must equal the wallet's current network, checked before any network read. The refusal names both networks.
- **Binary values** are canonical base64url (RFC 4648 section 5) with no padding: `=`, `+` and `/` are refused, a length of 1 mod 4 is refused, and non-zero trailing bits are refused, so each value has exactly one encoding.
- **Ids** are base58, at most 45 characters, decoding to 32 bytes.
- **`cb`** (optional on both verbs) follows the [Callback](#callback) rules. A `cb` that breaks them refuses the request.
- **Statuses.** The same six `ac` values on both verbs (see [Callback](#callback)).

### Wallet rules for `sign`

`sign` asks the wallet to sign one state transition the app built and cannot sign itself, for example an IdentityUpdate that needs the MASTER key, a batch with a token transition that needs a CRITICAL key, or a credit transfer. The app keeps its own session key for everything that key can do.

1. **Decode** the transition with a bounded decoder. Refuse (`invalid`) what does not decode, and what is already signed.
2. **Refuse a foreign transition.** It must be for the identity that is active in the wallet. If it is for another identity the wallet holds, name it and tell the user to switch; never switch identity silently. Check again after the PIN prompt.
3. **Choose the key.** Take the lowest eligible key: enabled on a fresh read of the identity, **unbound, unbudgeted and non-expiring** (so never an App Connect session key), with the purpose and level Platform requires for that kind of transition (for example MASTER for an IdentityUpdate, CRITICAL for a batch with a token transition or a contract update, a TRANSFER key for a credit transfer). Among the keys Platform accepts, prefer the least-privileged level, then the lowest key id. With no eligible key the wallet says so and answers `failed`.
4. **Describe it.** The sheet says in plain words what the transition does and which identity and key sign it. An IdentityUpdate says it changes the identity's keys and needs the MASTER key. A group-bound key's scope says "including contracts added to the group later". A token purchase says it needs the CRITICAL key. A non-zero `userFeeIncrease` is shown.
5. **Nothing is refused on kind.** The wallet does not turn a transition away because of what it is (an IdentityUpdate is shown, not refused). A kind it cannot describe needs an explicit advanced-settings confirmation; without it the answer is `unsupported`.
6. **Sign as given.** The wallet signs the transition's canonical bytes, overwriting any `signaturePublicKeyId` the app put in, keeps the signed bytes until the outcome is known, and broadcasts them. Retrying re-broadcasts the identical bytes; if the first copy landed, Platform refuses the second as a used nonce, which proves the first landed.
7. **Report.** There is no response document. The app polls for the effect and stops at `exp` plus 5 minutes; `cb`, if present, is only a prompt to look. A stale nonce or revision at broadcast is `stale`.

| `ac` | `connect` | `sign` |
| --- | --- | --- |
| `ok` | keys registered and the response published | signed, and the broadcast was accepted |
| `declined` | the user declined | the user declined |
| `stale` | `CREATED_AT` too old or too far ahead | `exp` passed, or the nonce or revision is out of date |
| `unsupported` | an unknown version, even TLV or binding kind | an unknown `v`, or a kind the wallet cannot describe |
| `invalid` | malformed, or it breaks a wallet rule (owner consistency, levels, budget) | malformed, already signed, or no owner |
| `failed` | approved, but registering or publishing failed | wrong network or identity, no eligible key, anything else |

An app maps an unknown `ac` value to `failed` and keeps polling.

### Moving from `dash-key:` to `dashpay://`

Wallets accept both carriers while the apps switch, and every `connect` request ends in the same decoder, sheet, grant and response. From the first wallet build that accepts `dashpay://connect`, `dash-key:` requests for mainnet (`n=m`) are refused, so mainnet never sees the legacy carriers. A web app cannot tell which wallet or version will open a link, so an app should switch its emitted carrier only when the wallets it targets accept `dashpay://`. `dash-key:` and `dash-st:` are removed from the wallets before App Connect is enabled on mainnet.

## App identity

An app is its `appId`, a contract id, and nothing more. There is no manifest, on chain or in the wallet. A manifest could not show that an app is genuine: anyone can deploy a contract and publish an owner-only record that calls itself "Yappr", which proves who wrote the record and not who they are. Platform's merged response contract has no manifest either. Yappr's anchor contract has an owner-only `appInfo` document ([APP_CONNECT_CONTRACTS.md](APP_CONNECT_CONTRACTS.md)); it is metadata for the owner, and wallets do not read it or enforce it.

What the wallet does with an `appId`. This is the intended wallet behaviour; some wallet builds today still warn on an unknown app id.

- **Shows the id.** The approval sheet always has an app id line, the base58 id shortened to its first 6 and last 6 characters, with the full id and a copy action one tap away.
- **Marks the label as unverified.** The name line is the brand-map name if the wallet knows the id; otherwise it is the request's label in quotes, marked as given by the app. It never has a "verified" badge, check mark or colour.
- **Never refuses an unknown app.** An id the wallet does not know gets a neutral "Not a known app" note: no warning colour, no extra step, no refusal.
- **Uses its brand map as a label only.** The brand map is a table inside the wallet from app id to a friendlier name. It gates nothing: not the callback, not the limits, not the keys.

The user is protected by seeing the id and every scope, budget and expiry, and by Platform enforcing each key's bounds, budget and expiry. Some structural rules hold for every app and none of them needs to recognise it:

- Owner consistency (wallet rule 3): a request cannot show app X while asking for keys on a contract X's owner does not control.
- Planned: a system contract (DPNS, DashPay and the like) may not be the `appId`. Rule 3 and the reference responder do not enforce this yet.
- `IDENTITY_HINT`, when present, must be the identity the wallet signs in.

## Callback

`cb` is an absolute `https` URL without credentials, at most 512 characters after decoding, optional on both verbs. It is only a nudge: the app polls immediately when it arrives and never treats it as proof of anything. The wallet appends `ac=<status>` (keeping any existing query) and follows one rule for every app, with no brand-map lookup:

- It shows the `cb` host on the approval sheet.
- A request that arrived as a **link** (tapped, or opened by the OS): once the user has approved or declined, the wallet opens `cb`. The user saw the host before choosing, and `cb` carries nothing but `ac`.
- A request **scanned inside the wallet** never opens `cb`.
- When there is **nothing to approve** (a refused request, or one that failed to parse), the wallet shows the reason and, if it has a valid `cb`, offers "Return to `<host>`"; it opens `cb` only on that tap.

Some wallet builds today still compare `cb` with a host their brand map holds for a known app and refuse a mismatch. The intended rule has no such check.

## Response

The wallet publishes a `loginKeyResponse` under the approving identity:

| Property | Value |
| --- | --- |
| `appEphemeralPubKeyHash` | `hash160(appEphPub)` |
| `walletEphemeralPubKey` | the wallet's fresh compressed ephemeral public key |
| `encryptedPayload` | `nonce (12) ‖ ciphertext ‖ tag (16)` |

### Crypto

```
shared = ECDH(walletEphPriv, appEphPub).x                         (32 bytes)
key    = HKDF-SHA256(ikm = shared, salt = "dash:key-exchange:v1", info = "app-connect:v2", 32 bytes)
aad    = "dash:app-connect:v2" ‖ hash160(appEphPub) ‖ $ownerId      (19 + 20 + 32 bytes)
body   = AES-256-GCM(key, nonce, aad, slot₀ ‖ slot₁ ‖ … ‖ slotₙ₋₁)
```

- The salt is the legacy key exchange's; the `info` string is new, so a v2 key never equals a v1 key.
- `$ownerId` is the raw 32-byte id of the identity that publishes the response. A response copied under another identity does not decrypt.
- The nonce is 12 random bytes, fresh per response.

### Payload

Each slot is a 32-byte secp256k1 private key. Slots are ordered: granted auth bindings in request order, then granted encryption bindings in request order. A declined binding has no slot. The payload is `28 + 32n` bytes with `1 ≤ n ≤ 17` (the schema's 60–572 bytes); for v2, `n` is at most the number of bindings.

The app does **not** rely on slot order: it classifies each key by finding it on chain.

## Wallet rules

1. **Decode strictly.** Refuse with `unsupported` or `invalid` as above. A wallet with several identities asks which one signs in; with an `IDENTITY_HINT` it offers only that one.
2. **Freshness.** Refuse a request whose `CREATED_AT` is more than 10 minutes before the wallet's clock, or more than 2 minutes after it (`stale`).
3. **Owner consistency.**
   - `appId` must be an existing contract, and a contractGroup binding's group must exist; otherwise the request is `invalid`.
   - A contractGroup or singleContract binding must be owned by the owner of `appId` (the group's owner, or the contract's owner).
   - A documentType binding on a contract owned by someone else is allowed only for system document types the wallet allowlists. This profile allowlists exactly one: DashPay `profile`. Never DashPay `contactRequest`, and never DPNS.
   - An `ENC_BINDING` contract must be `appId`, and that contract must opt in to identity encryption (or decryption) bounded keys for that purpose.
4. **Levels.** A contractGroup key may be CRITICAL or HIGH, never above what the binding asks. Every other auth key is HIGH. Encryption and decryption keys are MEDIUM. A wallet never grants a MASTER key, an unbound authentication key or a TRANSFER key through App Connect.
5. **Limits.** Every auth key is a V1 key: it carries a budget and an expiry, so a binding that proposes no expiry still gets one (the reference wallet uses 90 days), and a binding whose proposed expiry is already past is `invalid`. A contractGroup key always has a budget. Clamp the proposals and offer presets. The values below are recommended wallet policy, not protocol:

   | | Presets | Cap |
   | --- | --- | --- |
   | Budget | 0.1 / 0.5 / 2 DASH | 5 DASH |
   | Lifetime | 30 / 90 / 365 days | 365 days (default 90) |

6. **Auth keys.** One fresh key per granted auth binding, derived at DIP-13 sub-feature `6'`. The derivation is normative, so that every wallet derives the same key for the same request and binding:

   ```
   m / 9' / coin' / 5' / 6' / 0' / identityId' / requestId'
   requestId = hash256(appEphPub33 ‖ u8(bindingIndex))
   ```

   `coin'` is `5'` on mainnet and `1'` elsewhere. `identityId'` and `requestId'` are 256-bit hardened levels (DIP-14). `appEphPub33` is the request's compressed public key, `hash256` is SHA-256 applied twice, and `bindingIndex` (0–3) is the binding's position in the **request**, declined bindings included, so the key does not depend on what the user declined. Binding 0 uses `u8(0)` too. A bare `hash256(appEphPub)` stays reserved for the legacy one-QR key, so a v2 key can never collide with it. dashwallet-ios and dash-wallet derive keys this way. Yappr's test responder does too, but only for personas with a recovery phrase; personas without one use a test-only HKDF scheme (`mobile/tools/src/app-connect/derive.ts`) that no wallet uses.

   Two properties follow, and they are why the leaf is what it is:
   - Each granted key is distinct from every other key on the identity, including the other keys in the same response.
   - Each granted key is deterministic for a given (request, binding), so a retry of the same request (a crash before the update confirmed, a second tap) re-derives the same key and adds no new ones.

   Keys under `6'` are never recovered from the seed, and wallets do not scan this path during identity recovery. The app never re-derives an auth key: it takes each private key from the response, finds the matching public key on the identity on chain, and checks that key's bounds, level and limits against the request. Keys may be ECDSA_SECP256K1 or ECDSA_HASH160; both wallets register ECDSA_HASH160.
7. **Encryption key.** One key per (identity, `appId`, purpose), shared by every device of the user and derived at DIP-13 sub-feature `7'`:

   ```
   m / 9' / coin' / 5' / 7' / 0' / identityId' / appId' / purpose'        purpose 1' ENCRYPTION, 2' DECRYPTION
   ```

   This derivation is normative: peers and other wallets must find the same key. (As with rule 6, the test responder follows it only for personas with a recovery phrase.) It is the sub-feature `7'` path built in rust-dashcore#1049 and dips#191. The key is ECDSA_SECP256K1 (peers need the point), MEDIUM, bound `singleContract(appId)`. There is no rotation index: this profile defines one key per (identity, `appId`, purpose), and replacing it is not defined.
   - If the identity's current key for `appId` (what `identities.contractKeys` returns) is one this wallet can derive, **re-send it** and register nothing.
   - If the identity has none, register it and send it.
   - If it has one this wallet cannot derive (another wallet made it), **omit the slot**. Omit it too when the wallet's own key is on the identity but disabled or no longer current.
   - A login never replaces or adds a second key.
8. **One identity update.** A single MASTER-signed IdentityUpdate adds the new keys (and the encryption key if it was missing) and disables the auth keys of the previous grant for the same (identity, `appId`, `CONNECTION_ID`). Without a `CONNECTION_ID` nothing is disabled. Platform adds at most 6 keys per update, which this profile never exceeds (4 auth + 2 encryption).
9. **Publish.** Wait until the update is confirmed. Then delete the previous response the wallet published for this identity and app, using an index-only delete carrying all three original values, and create the new response. These are two transitions, because Platform allows one transition per document batch. Both are signed by an unbound, unbudgeted, non-expiring AUTHENTICATION key of the identity at HIGH or CRITICAL. The delete is best effort and never blocks the login: a failed delete is retried at the next login. Deleting a response does not revoke keys.
10. **Callback.** Open `cb` as described [above](#callback).

### Approval sheet

Say what the app can do, what it can spend, and for how long, in plain words, and say what it cannot do. Yappr's sheet should read close to:

> **Yappr** wants to sign in as **@alice**.
>
> Yappr can post, like, follow, message and edit your DashPay profile, spending up to **0.5 DASH** until **9 January 2027**. It cannot send your credits, register names or change your keys.
>
> Requested 12 seconds ago · returns to yap.pr
>
> Only approve if you just started signing in on yap.pr.

- The app line follows [App identity](#app-identity): the id shortened with copy, the brand-map name or the label in quotes as the app's own claim, and "Not a known app" for an unknown id. No warning, no extra step.
- One line per granted binding; optional bindings are toggles.
- Show the budget in DASH, not credits, and the expiry as a date.
- Show the request age and the callback host (or that the request does not return to a website).
- For a group-bound key, say that it also covers contracts added to the group later.
- For a CRITICAL group key, the line about tokens: "It can also claim and spend this app's tokens on your behalf."
- The closing line names what the request itself shows (the callback host, else "this app"), not a host from the brand map.

## App rules

These are what `vendor/platform-auth/src/app-connect/` implements.

**Polling.** Query `loginKeyResponse` with `appEphemeralPubKeyHash == hash160(appEphPub)`, ordered by `$ownerId`, 10 per page, paging after the last owner; with a hint, add `$ownerId == hint`. Poll every 2 s for the first minute, then every 4 s, and immediately on focus or callback. Give up after 10 minutes, or after 20 candidates ("start again").

**Verification.** A candidate is accepted only if all of these hold, with proved reads:

1. With an `IDENTITY_HINT`, the candidate's `$ownerId` equals it.
2. The payload framing is `28 + 32n`, with `n` no larger than the number of bindings, and it decrypts with the AAD.
3. Every slot is a key on `$ownerId` (by point for ECDSA_SECP256K1, by `hash160` for ECDSA_HASH160) that is not disabled.
4. Every auth key has bounds equal to one requested binding, an allowed level for it (rule 4), and the limits the binding asked for, including the group key's budget.
5. Every encryption key is MEDIUM, ECDSA_SECP256K1, bound `singleContract` to an `ENC_BINDING` contract with the same purpose, and is the key `identities.contractKeys` currently returns.
6. No key is MASTER, unbound, of another purpose, bound to anything not requested, or granted twice; no binding gets two keys.
7. The primary binding is granted.
8. No key expires within an hour of the latest block time, and every budgeted key has a remaining budget above zero.

Anything else rejects the whole candidate. A key that is not visible yet is retried for a few seconds (the app's node may lag the wallet's).

The same checks run against keys an app kept from an earlier grant (`verifyAppConnectKeys`; Yappr's passkey vault re-checks the keys it sealed this way, [PASSKEY_VAULT.md](PASSKEY_VAULT.md)). A refusal says why, so an expired or spent grant leads to a renewal in the wallet rather than a dead session.

**Identity confirmation.** Anyone can answer a request, including with their own identity. With a hint, only that identity is accepted. Without one, the app always asks "Continue as @alice?" with the avatar and name, and offers a chooser when several candidates verify.

**Group trust.** Before offering App Connect, the app proves that the group's owner and admins are the ones it pinned and that its members are exactly the pinned set. A group-bound key may sign for every member the group ever gains, so an unexpected member or owner blocks new logins.

**Signing.** The session is a key ring. Before building a write, the app picks the narrowest usable key that covers every batch member (a documentType key, then a contract key, then the group key, using the pinned members), including every document type a create consumes. It requires CRITICAL for any batch with a token operation and the strictest `securityLevelRequirement` of the members' types, never uses a bound key outside a batch, skips keys about to expire or short of budget, and splits a batch no single key covers (a DashPay profile plus a Yappr profile). As long as the caller describes the batch accurately, the paid out-of-bounds refusal (20014) cannot happen.

## Errors

| Code | Platform error | App action |
| --- | --- | --- |
| 20013 | `ContractBoundedKeyNonBatchError` | A routing bug: send the write to the wallet and log it. Unpaid. |
| 20014 | `ContractBoundedKeyOutOfBoundsError` | Should be impossible. Paid. Drop cached budgets and bounds, show a generic error, log loudly. |
| 20015 | `PublicKeyBudgetExhaustedError` | The allowance is spent. Reads continue; ask to renew. Unpaid. |
| 20016 | `PublicKeyExpiredError` | The key expired. Reads continue; ask to renew. Unpaid. |
| 40218 | `IdentityPublicKeyBudgetExceededError` | This write needs more than is left. Say how much, then ask to renew. Unpaid. |
| 20006, 40208 | key disabled | Revoked in the wallet: sign out and wipe the session. |
| 20003 | `MissingPublicKeyError` | The key is gone: sign out and wipe the session. |
| 20004, 20007 | security level not met | Send the write to the wallet. 20004 is paid when a batch member's type requires a higher level. |

"Send the write to the wallet" means `dashpay://sign` once it exists. Today that is a `dash-st:` link, or a step-up prompt for a typed key.

## Renewal

Renewal today is a **new login** that carries the same `CONNECTION_ID` and the identity as `IDENTITY_HINT`: the wallet registers fresh keys and its one IdentityUpdate (rule 8) disables the old ones. This is what Yappr does, and it works whichever carrier either request used.

`MODE = 1` (renew) is part of the body, but no app sends it yet and this profile does not fix its semantics. A wallet that supports it raises the limits of the existing keys in place and republishes, and the app checks the result with the same verifier as any other response. The reference responder (`mobile/tools/README.md`, "Renew and revoke") adds the proposed budget to each key's total up to the cap, moves each expiry only later, and answers as a new login when an old key lacks a level or limit the request needs. Those details are wallet-defined, not part of the protocol.

## Yappr's request

This section and the next describe Yappr, as an example consumer of the profile. They are app policy, not protocol.

| | Value |
| --- | --- |
| `appId` | the `yappr-app` anchor contract ([APP_CONNECT_CONTRACTS.md](APP_CONNECT_CONTRACTS.md)). It creates the group, opts in to `requiresIdentityEncryptionBoundedKey: 2`, and has one owner-only `appInfo` type that no wallet or app reads |
| label | `Yappr` |
| Binding 0 (primary) | contractGroup, the anchor's group, **CRITICAL**, 50,000,000,000 credits (0.5 DASH ≈ $30), 90 days |
| Binding 1 | documentType, DashPay `Bwr4WHCPz5rFVAD87RqTs3izo4zpzwsEdKPWUT1NS1C7` `profile`, HIGH, 1,000,000,000 credits (0.01 DASH ≈ 60¢), 90 days |
| `ENC_BINDING` | the anchor, ENCRYPTION |
| `CONNECTION_ID` | 16 random bytes per browser or device and network, kept across logouts |
| `cb` | `https://yap.pr[/prefix]/connect/?r=<hex hash160(appEphPub)>`; the mobile app adds `&app=<scheme>` so that page opens the app |

The group has no admins. Its members are the anchor and the release contracts (social, blocks, DM v5, blog, pollr, storefront and the passkey vault); [APP_CONNECT_CONTRACTS.md](APP_CONNECT_CONTRACTS.md) has the pinned list and versions. The legacy key exchange, password vault, key backup and DM v4 contracts stay out of it. 0.5 DASH is roughly 300 posts or 3,000 likes at current fees.

**Why CRITICAL.** Platform requires CRITICAL for any batch that contains a token transition, and Yappr's 100-YAPP starter claim is one. Bound to the group, a CRITICAL key adds only token operations on the group's tokens: YAPP cannot be transferred and the user holds no token authority, so in practice that is claiming and spending the user's own YAPP. The app still signs every other write with the narrowest key, and accepts a HIGH group key (the claim is then unavailable in the app).

**Still outside App Connect:** credit tips (TRANSFER), DPNS registration, revoking keys and raising limits, and contract moderation. Where these need the wallet, today they use `dash-st:` links or a typed key. The planned `dashpay://sign` replaces the `dash-st:` ones.

## Recovery-phrase sign-in (Yappr, D38)

An app may also sign a user in with their wallet's recovery phrase. It has to
derive exactly what a wallet holding the phrase derives, or the user's messages
are lost the next time they sign in with the wallet. Yappr follows the reference
wallet (dashwallet-ios #1210, rs-platform-wallet, key-wallet), in
`lib/crypto/dip13.ts` and `lib/auth/recovery-phrase-sign-in.ts`:

- **Identity:** DIP-13 discovery. For identity index 0, 1, ..., derive
  `m/9'/coin'/5'/0'/0'/index'/0'` (the MASTER key) and look the identity up by
  that key's hash160. Stop after 5 unused indexes in a row (`IDENTITY_GAP_LIMIT`).
- **Session key:** each enabled key of the identity is derived at key index =
  key id and kept only if it matches. The session signs with the HIGH
  authentication key, else the CRITICAL one, stored as if it had been typed in.
- **Encryption key:** rule 7's key. It is current: use it. None:
  add it in one MASTER-signed IdentityUpdate, with the phrase's MASTER key, and
  wait until `contractKeys` returns it. Another wallet's key, or this key
  disabled: leave it alone, and say messaging was set up with another wallet.
- **The phrase** is never stored, logged or sent. Its field is cleared once
  used.
- **Not on mainnet yet:** the app's CSP still allows inline scripts, so an
  injected script could read a phrase that controls real funds. Mainnet builds
  offer wallet sign-in only until the CSP is tightened (`recoveryPhraseOffered`).

A typed-in private key still signs in. On App Connect builds, a messaging key
derived from it (HKDF info `yappr/app-connect/encryption-key/v1:<anchor>`) is a
developer option only: no wallet derives it.

## Test vectors

All inputs are fixed so the outputs are reproducible. Each 32-byte seed is `sha256("dash app-connect v2 vector/" + label)`: `app ephemeral`, `wallet ephemeral`, `app id`, `group id`, `owner`, `slot group key`, `slot dashpay profile key`, `slot encryption key`; the connection id is the first 16 bytes of `sha256(… "connection id")` and the nonce the first 12 bytes of `sha256(… "nonce")`. The request is Yappr's (with placeholder anchor and group ids), created at 2026-10-11T00:00:00Z with both keys expiring 90 days later, on devnet with a callback. The renew request is the same with only the group binding, `IDENTITY_HINT` = the owner and `MODE` = renew, on testnet without a callback.

- `request.bytes` is the body; `request.uri` the URI.
- `response.sessionKey` is the HKDF output; `response.aad` the AAD; `response.plaintext` the three slots concatenated (group, profile, encryption).
- `response.encryptedPayload` is the nonce, ciphertext and tag; `response.slotPublicKeys` and `response.slotPublicKeyHashes` are what the identity update registers (as ECDSA_SECP256K1 or ECDSA_HASH160 data).

`vendor/platform-auth/src/app-connect/vectors.json` holds the same values, and `vectors.test.ts` checks that the code reproduces them, that this block matches, and that an independent AES-256-GCM decrypts the payload.

The vectors use the `dash-key:` carrier. Vectors for `dashpay://connect` (the same bodies as canonical base64url) and for `dashpay://sign` will be added when those carriers are implemented.
